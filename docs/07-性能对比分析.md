## 一、核心结论

1. **速度天花板由"技术路线"决定，不由语言/品牌决定。**
   - Windows 上直读 NTFS **MFT**（WizTree、disktree 提权整盘）完胜一切目录遍历工具；
   - Linux/macOS 上 **rayon 并行遍历**（dust / dua / disktree 普通模式）是实用天花板；
   - `du` / `ncdu -o` 的**流式遍历**在内存和单核小机器上反而最稳。
2. **disktree 是目前唯一同时具备"Rust 高性能内核 + 跨三平台 + GPU treemap + 安全删除 + SSH 只读扫描"的开源工具**——它的护城河是"全平台 + 可视化 + 安全"，不是单纯扫描速度。
3. **"比 WizTree 快 3 倍"只在「管理员 + 整块 NTFS 盘」这个最佳条件成立。** 日常扫子目录 / 未提权时退化成普通遍历，此时**慢于 WizTree**（WizTree 把提权直读做成默认路径）。
4. **对 treesize 的总判断**：treesize 在 Windows 上已有 MFT/USN 引擎规划，方向正确；真正要补的不是"再快一点"，而是**口径对齐 `du`/WizTree、内存模型讲清楚、删除安全、整盘记忆化**这几件产品级功课（详见第六节）。

## 二、技术路线分野（决定性能上限）

| 阵营 | 代表工具 | 扫描方式 | 速度量级 | 内存特征 |
|---|---|---|---|---|
| **MFT 直读**（仅 NTFS） | WizTree、**disktree（提权整盘）** | 绕过 API 直读主文件表 | 秒级（最快） | 与文件数无关 |
| **并行遍历** | **disktree（普通）**、dust、dua、gdu | rayon / 多线程 `read_dir` | 中快（受核数 + SSD 并发影响） | dust/gdu 随文件数线性涨；dua 流式则恒定 |
| **流式遍历** | `du`、`ncdu -o`、`diskus` | 走一层丢一层，只留累加值 | 单核小机反而最快 | **恒定 3.6–4.9 MB** |
| **单线程遍历** | WinDirStat、TreeSize Free、SpaceSniffer | 递归枚举 | 偏慢 | 随文件数涨 |

> **关键认知**："比 `du` 快"是有前提的。dust/gdu 的加速来自多线程，前提是**多核 + 能并发随机读的 SSD**；在单核 VPS 上反而更慢（DevLearn 2026 实测：单核机上 `du` 是最快最省内存的）。

## 三、性能基准数据

### 3.1 命令行工具 Linux 基准（gdu 作者，清除缓存后测量）

> 绝对值不可跨机器比较，**只看相对排序**。该基准**不含 disktree / WizTree / 任何 GUI 工具**（纯 Linux CLI）。

| 工具 | 语言 | 冷缓存 (s) | 热缓存 (ms) | 相对 |
|---|---|---:|---:|---:|
| diskus | Rust | 3.07 | 211 | 1.00 |
| gdu -npc | Go | 3.13 | 434 | 1.02 |
| pdu | Rust | 3.77 | 222 | 1.23 |
| dust -d0 | Rust | 4.00 | 364 | 1.30 |
| dua | Rust | 5.32 | 451 | 1.73 |
| du -hs | C | 14.94 | 809 | 4.86 |
| ncdu -0 -o /dev/null | C | 15.69 | 1433 | 5.10 |

结论：Rust/Go 现代工具在 Linux 上约为传统 `du`/`ncdu` 的 **3–5×**；其中 `diskus`/`pdu` 走"最简/流式"路线在热缓存下最快。

### 3.2 Windows 原生 GUI 工具（社区实测，定性结论）

| 工具 | 扫描方式 | 速度 | 免费 |
|---|---|---|---|
| **WizTree** | NTFS MFT 直读 | 极快（25GB HDD **4.3s** vs WinDirStat 3min20s = **46×**；460GB SSD **5.2s** vs 1min55s = **22×**） | 个人免费 |
| **disktree（提权整盘）** | NTFS MFT 直读 | 4M 文件 C:\ ≈ **3.4s**（作者自测） | 免费 MIT |
| TreeSize Free | 目录遍历 | 中等偏慢 | 个人免费 |
| SpaceSniffer | 目录遍历 | 中等，大盘会卡 | 免费 |
| WinDirStat | 目录遍历 | 偏慢 | 开源免费 |

### 3.3 disktree 作者自测（写进代码注释，可复现但为单次/单机）

| 场景 | 数据 |
|---|---|
| 4M 文件 C:\ MFT 直读 | disktree **3.4s** / WizTree 11.2s / 普通遍历 ~20s |
| 3.4M 文件家目录遍历 | 16 线程 **6.5s** / 24 线程 **8.1s**（线程并非越多越好） |
| BitLocker 卷吞吐 | 1MiB×16 线程 2 GB/s → 16MiB 块 **4.2 GB/s** |
| 1.6M 文件 / 762GB 遍历模式 | ~**40s**（典型 NVMe） |

### 3.4 数据可信度与边界（重要，避免误读）

- disktree 的 **3.4s vs WizTree 11.2s** 是**作者自报、单次、特定机器**，且 WizTree 侧版本/测量条件未公开；WizTree 官网自测约为 5s 量级，二者不直接可比。
- 社区（techfm 评测）明确指出：**日常扫子目录时 disktree 仍慢于 WizTree**，"快 3 倍"仅在整盘 + 提权成立。
- gdu 基准（3.1）是独立第三方，但**不含 disktree / WizTree / GUI 工具**，不能与 3.2/3.3 直接相加。
- Windows GUI 对比多数来自中文科技博客，非严格基准，**看定性结论即可**（MFT 远快于遍历）。

## 四、disktree 深度剖析

### 架构亮点（性能向）

- **扫描内核照搬 dust 路线**：`rayon::scope` 每根一个、**递归深度恒为 O(1)**（不会因深目录爆栈）；每目录一个原子完成计数器 + 哨兵，确保"子目录全到齐才构建父目录"；大小汇总与硬链接去重在**自底向上单趟**完成。
- **Windows MFT 快路径**（`mft.rs`）：16 MiB 大块 + `FILE_FLAG_NO_BUFFERING` 绕缓存 + 按 `$BITMAP` 只读在用记录；连"多读一段自由区比重新发起读更便宜"都做了实测调参（含 BitLocker 吞吐对比）。
- **记忆化扩展**：从 `~` 扩到 `/` 只扫新增部分、复用已测子树（"秒级而非整盘重扫"）——低成本高感知的 UX 优化。
- **SSH 只读扫描**：helper 流式 DFS 直吐 stdout，**内存随"打开的祖先层数"而非文件数增长**，1GiB 地址空间上限 + 5 分钟超时 + 无 sudo。

### 性能边界（决定它能否对标 WizTree）

- **MFT 捷径仅在「管理员权限 + 整块 NTFS 盘」组合触发**；扫子目录或未提权 → 退化成普通遍历，此时慢于 WizTree。
- **并行不是银弹**：24 线程比 16 线程更慢，超过物理核后锁/上下文竞争反噬。

### 与同类差异点

GPU 加速 treemap（GPUI）、"Worth a look"智能清理建议、标记-复核-回收站三步删除 + 拒绝清单（系统目录/挂载点/商店目录）、跨三平台单一程序、硬链接只算一次、默认磁盘占用 `st_blocks×512`（与 `du` 口径一致）。

| 工具 | 平台 | 模式 | 速度档 | 免费 | treesize 可借鉴点 |
|---|---|---|---|---|---|
| WizTree | Win | MFT 直读 | ★★★★★ | 个人免费 | 提权直读是 Windows 速度制高点 |
| disktree | Win/Mac/Lin | MFT + 并行 + SSH | ★★★★~★★★★★ | MIT | 三平台一致、treemap、安全删除、记忆化 |

## 六、对 treesize 的启示

treesize 当前是 Rust + DDD/TDD + egui + Treemap + 报表/TopN/去重 + rayon 并行，正处于同类赛道。结合本文与 `06`，可落地项：

1. **Windows 速度制高点 = NTFS MFT 直读。** 若要"全盘秒扫"对标 WizTree，必须有一条 MFT 直读路径（raw volume read），仅并行遍历在 Windows 上追不上 WizTree。Linux/macOS 以 rayon 并行遍历为实用天花板。（引擎细节见 `06` 第四节）
2. **线程数要给上限，别盲目并发。** 参考 disktree 16→24 线程反而变慢，默认用 rayon 全局池并允许 `--jobs` 上限。
3. **口径必须对齐 `du`/WizTree**，否则数字会被质疑：默认磁盘占用（非 apparent size）、硬链接 inode 去重只算一次、跨挂载点边界严格跳过。（treesize 已在 P0 把 Fs 引擎默认改为 `AllocationSize`，见 `06`）
4. **内存模型要讲清楚**：Treemap 必须全量建树，内存天然随文件数线性涨（dust/gdu 同病）；服务器/超大盘场景可加"只算 TopN + 采样"模式控制内存峰值。
5. **记忆化扩展**（`~`→`/` 复用子树）是低成本高感知的体验优化，建议在"整盘"模式借鉴。
6. **删除安全**：disktree 的"标记-复核-回收站"三步 + 拒绝清单非常值得 GUI 删除流程借鉴，防误删是清理工具的信任底线。

> **treesize 的护城河（disktree 没有，不可牺牲）**：USN 增量引擎、领域分层 + `ScanEngine` trait、资源限流、`blake3` 重复文件流水线、CLI+egui 双前端、扫描历史与趋势。性能追赶应建立在这五点之上，而非取代它们。
