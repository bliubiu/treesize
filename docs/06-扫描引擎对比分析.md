## 二、Windows 枚举层 —— 最大差距

disktree 的 `crates/disktree-core/src/windows.rs` 是整个项目最硬的部分，核心常量：

```rust
const BUFFER_BYTES: usize = 64 * 1024;              // windows.rs:46一次填满几百条记录
const NAME_AT: usize = offset_of!(FILE_ID_EXTD_DIR_INFO, FileName); // windows.rs:49
const NAME_SURROGATE: u32 = 0x2000_0000;            // windows.rs:54 符号链接/联接点/挂载点
const EVICTED: u32 = FILE_ATTRIBUTE_RECALL_ON_OPEN
    | FILE_ATTRIBUTE_RECALL_ON_DATA_ACCESS;         // windows.rs:61 云占位符
```

`Records::fill()`（windows.rs:296-319）直接调用：

```rust
GetFileInformationByHandleEx(
    self.handle.as_raw_handle(),
    FileIdExtdDirectoryInfo,
    self.buffer.as_mut_ptr().cast(),
    BUFFER_BYTES as u32,
)
```

一次调用即从每条记录取出：

| 记录字段 | 用途 | treesize 现状 |
|---|---|---|
| `FileName`（UTF-16，容错解码） | 名称 | jwalk 同样需要 |
| `FileAttributes` + `ReparsePointTag` | 区分 目录 / 链接 / 文件 | jwalk 需 `file_type()` |
| `EndOfFile` | 表观大小 | — |
| **`AllocationSize`** | **真实占用** | **缺失** |
| `LastWriteTime` | 修改时间 | 需额外 `metadata()` |
| `FileId`（128 bit） | 硬链接去重 / 环检测 | **缺失** |

### treesize 当前每个文件多花两次系统调用

`src/infrastructure/fs_scanner.rs:281-289`：

```rust
let is_symlink = entry.path_is_symlink();      // 额外查询
let is_dir = entry.file_type.is_dir();
let (size, modified) = match entry.metadata() { // 又一次
    Ok(meta) => {
        let sz = if is_dir { 0 } else { meta.len() };  // 仅逻辑大小
```

1000 万个文件 ≈ 多出 2000 万次元数据查询，且拿到的大小**低于真实占用**。

### disktree 额外处理的两个细节

- **非配对 UTF-16 代理项**（windows.rs:418-440）：显示为 U+FFFD，但保留原始 `OsStr`，
  保证路径仍能打开（Windows 遗留文件名）。
- **云占位符跳过**：`RECALL_ON_OPEN` 目录不进入，否则 OneDrive 会被触发下载 ——
  磁盘分析工具绝不应引发网络 IO。

## 三、遍历模型

### disktree：dust 形状的 PendingDir 计数

`scan.rs:678-716`：

```rust
struct PendingDir {
    parent: Option<Arc<Self>>,
    pending: AtomicUsize,   // 起始 1，每个子目录任务 +1，归零才构建节点
    partial: Mutex<Partial>,
    read_error: AtomicBool,
    depth: usize,
}
```

- 目录**仅在自身扫描 + 所有子目录任务都完成后**才构建节点 → 无锁竞争、无join 点
- 大小聚合在 `tree::aggregate` 一趟自底向上完成，硬链接去重同一趟
- `TALLY_EVERY = 1024`（scan.rs:853）：每 1024 条目才碰共享原子量。注释指出每个 worker
  每条目都加会让同一条 cache line 在核间弹跳
- 线程池 `WALK_POOL`（scan.rs:836-846）：Windows 上 `min(cores, 16)`，
  避免 64 线程把 SSD 队列深度打满；MFT 解析也 `install` 到同一池

### treesize：jwalk 扁平条目 + 事后建树

- `WalkDir::new(root).follow_links(opt).process_read_dir(...)`（fs_scanner.rs:213-259）
  原地分区过滤 + `read_children_path = None` 剪枝 —— **这一点做得不错，disktree 是在
  classify 之后才决定是否进入**
- 产出**全量扁平 `Vec<EntryData>` 驻留内存**，之后 `build_tree`（fs_scanner.rs:340-402）
  用 `Vec<Option<FileNode>>` arena + `HashMap<PathBuf, usize>` 反向挂载，O(n)
- 限流检查节流到每 1000 文件一次、进度每 5000 文件一次（fs_scanner.rs:122-152）——
  与 disktree 方向一致，都是自己摸出来的 cache line 优化

## 四、MFT 引擎对比

| 维度 | tobi/disktree（`mft.rs`，1713 行 / 13 测试） | treesize（`mft_scanner.rs` + `ntfs_reader.rs`） |
|---|---|---|
| 触发条件 | 整盘盘符 + `GetVolumeInformationW == "NTFS"` + 管理员（windows.rs:616-637） | `is_ntfs_volume()` 试探（ntfs_reader.rs:666） |
| 读取方式 | 按 `$DATA` 的 data run 分段读，`CHUNK_BYTES = 16MB` | **`read_mft_raw` 全量读入一个 `Vec<u8>`**（ntfs_reader.rs:215） |
| 空闲簇策略 | `GAP_BYTES = 1MB` 内跨过空闲区继续读（mft.rs:52） | 无 |
| 解析 | **rayon 并行解析 chunk**（mft.rs:546 `table()`） | `parse_mft_records` 串行 for 循环（ntfs_reader.rs:503） |
| 每记录开销 | 原地解析切片 | `parse_mft_record` 内 **`data.to_vec()`**（ntfs_reader.rs:393） |
| 上限保护 | `MOST_LEVELS = 1024`（防损坏记录成环）、`MOST_CONTENTS = 64MB` | `max_records = min(1亿, valid_data_length / bpr)`（mft_scanner.rs:95） |
| 属性支持 | `0x10/0x20/0x30/0x80/0xB0/0xC0`，含 `$ATTRIBUTE_LIST`、`$BITMAP`、`REPARSE_POINT` | `0x30` + `0x80`；`AttributeType::AttrList = 0x20` 虽在枚举中但**解析分支未处理** |
| 大小来源 | 记录级分配大小 | `DATA(0x80)` non-resident 的 **real size**（ntfs_reader.rs:413-417）；resident 文件回落到 `$FILE_NAME.file_size`（ntfs_reader.rs:372） |
| 删除后一致性 | `flush_volume()`（windows.rs:680，需管理员写句柄） | 无 —— 删完立即重扫会读到旧数据 |

### 读取参数的实测标定

disktree 把标定数据直接写进注释（mft.rs:36-53）：

> 通过 BitLocker，16 线程 × 1 MiB → 2 GB/s，16 线程 × 16 MiB → 4.2 GB/s；
> 每个请求固定成本约 0.29 ms + 0.23 ms/MiB。
> 400 万记录的 `C:\`：1 MiB 用时 3.44 s vs 4 MiB 用时 3.60 s（6 次交替取中位数）。
> 在合成记录上（每 2000 条约 600 条空闲），跨读 1028 ms vs 遇空闲即停 1209 ms。

### treesize 的 MFT 内存尖峰

400 万记录 × 1024 B ≈ **4 GB 一次性驻留**，再加 `data.to_vec()` 的逐记录副本。
`ResourceLimits.max_memory_mb` 只在 fs 引擎路径生效，MFT 路径绕过了它。

## 五、错误处理、取消、权限

| 方面 | tobi/disktree | treesize |
|---|---|---|
| 错误明细 | `MAX_ERROR_DETAIL = 50`，超出截断但**计数继续涨**（scan.rs:34） | 权限类错误降为 `debug` 避免刷屏（fs_scanner.rs:294），其余 `warn` |
| 错误计数 | `ScanProgress.errors` relaxed 原子 | `ScanState.errors` 原子 + `ScanService::count_errors` 递归全树统计（scan_service.rs:56） |
| 取消 | `ScanProgress.cancelled`，UI 直接轮询 | `CancelToken`（`Arc<AtomicBool>`），每条目检查 |
| 进度快照 | 纯 relaxed 原子，明确注释"是进度表不是同步点，允许滞后几条" | 同思路，进度节流 5000 文件 |
| 权限不足 | 降级为遍历 + 面板提供 **Restart as Administrator**（UAC `runas` 重启，`windows.rs:645`） | `open_volume` 失败即返回 `ScanFailed` |
| 不可读目录 | 计数并上报，从不致命 | 计错误、跳过、继续 |

## 六、treesize 的独有优势（改进时不可牺牲）

1. **USN 增量引擎**（`usn_scanner.rs` + `FSCTL_READ_USN_JOURNAL`）——
   disktree 完全没有。能"只扫上次之后变更的部分"，是数量级差异。
2. **`ScanEngine` trait 领域抽象** + `ScanService` 编排 + `MockScanEngine` 测试替身——
   disktree 的 `scan()` 是自由函数，扩展引擎需改核心代码。
3. **资源限流**（`ResourceLimits`：文件数 / 时间 / 内存）+ `MemoryMonitor`——
   disktree 只有 `--threads`。
4. **扫描历史持久化**（rusqlite bundled）+ `ScanHistory` / `TrendService` 趋势对比。
5. **blake3 七阶段重复文件流水线**（大小分桶 → 头部哈希 → 快速去重 → 全量哈希）——
   disktree 完全没有这个维度。
6. **CLI + egui 双前端**、中文内嵌字体、`ScanOptions` 可 serde 序列化、跨平台（Linux/macOS 可编译）。

| 优先级 | 改动 | 预期收益 | 改动面 |
|---|---|---|---|
| **P0** | fs 引擎改用 `GetFileInformationByHandleEx(FileIdExtdDirectoryInfo)` 枚举 | 每文件省 2 次 syscall，大盘扫描可快 1.5–3× | ✅ 已完成：`infrastructure/{win_enum,dir_reader}.rs` + 重写 `collect_entries` |

## 八、本次实施范围与落地结果（2026-10-02）

落实 **P0** 两项，已全部编译通过、单元测试通过（`cargo test --lib` 102 passed）。

1. 新增 `src/infrastructure/win_enum.rs`
   - `GetFileInformationByHandleEx(FileIdExtdDirectoryInfo)` + 64 KB 8 字节对齐缓冲
   - 一次调用取出 name / kind / apparent / allocated / mtime / reparse tag

     却到列举时才回"不支持"，提前探明才能干净回落，而不是吐半个目录后失败

   - 打开失败 / 不支持该列举方式 → 回落 `std::fs::read_dir` + `entry.metadata()`

   并提供 `allocated_size_of()` 给单文件扫描路径
3. 重写 `fs_scanner::collect_entries` 为 `rayon::scope` 结构化并发遍历，去掉 jwalk
   - 计数按批（1024 条）提交，避免每条目争抢同一条原子量
   - `MemoryMonitor` 加锁（`check_limits` 已节流到每 1000 文件一次）
   - 深度与树深度解耦，工作栈 O(1)
4. `ScanOptions` 新增 `apparent_size`（默认 `false` = 分配大小），CLI 新增 `--apparent-size`
5. 顺带闭合 `follow_links=true` 的环检测（用 `canonicalize` 后的真实路径去重，

### 与原计划的偏差

| 原计划 | 实际 | 原因 |
|---|---|---|
| 一次调用取出 `fileId` | 未取 | 硬链接去重是 P1；本轮只闭环检测 |
| 云占位符标记 `evicted` | 未做 | 需要 `RecallOnDataAccess` 属性位，属 P2 |
| 环检测用 `file_id` | 用 `canonicalize` 真实路径 | 同上；语义等价且不依赖新字段 |

### 大小口径的实测结论（重要）

`AllocationSize` 并不是简单的"按簇向上取整"。在 NTFS 上实测（4 KB 簇）：

| 文件长度 | `EndOfFile` | `AllocationSize` |
|---:|---:|---:|
| 1 | 1 | **8** |
| 100 | 100 | 104 |
| 700 | 700 | 704 |
| 1000 | 1000 | 4096 |
| 4096 | 4096 | 4096 |
| 4097 | 4097 | 8192 |
| 100010（稀疏） | 100010 | 102400 |

规律：**小于约 700 字节的"常驻文件"（数据直接存在 MFT 记录里）报字节级分配，
超出后才是整簇**。所以默认口径改成 `AllocationSize` 后，一批 1 字节的小文件
会从"共 1 字节"变成"共 8 字节"——比资源管理器的 4 KB 少，但比原来的逻辑长度准。
`FileIdExtdDirectoryInfo` 与 `FileStandardInfo` 两个 API 实测完全一致，
不是解析错误。

需要"和资源管理器逐字节对齐"的用户应改用 MFT 引擎读 `$STANDARD_INFORMATION`。

P1 及以后见上表，本次不做。

## 九、MFT 引擎修复记录（第二轮）

上一节记录的"MFT 完全不可用"有两个独立根因，都已修复。

### 根因 1：几何字段取自错误的结构偏移

原 `get_volume_info` 按 MSDN 的 `NTFS_VOLUME_DATA_BUFFER` 布局从
`FSCTL_GET_NTFS_VOLUME_DATA` 取 `SectorsPerCluster@16 / BytesPerSector@24 /
BytesPerCluster@32 / BytesPerFileRecordSegment@40`。实测（Windows 11 / 4 KB 簇）：

| 偏移 | 假定字段 | 实测值 | 真实值 |
|---:|---|---:|---:|
| 0 | VolumeSerialNumber | 有效 | ✓ |
| 8 | NumberSectors | 487135231（= C: 容量 ÷ 512） | ✓ |
| 16 | SectorsPerCluster | 60891903 | **8** |
| 24 | BytesPerSector | 29397102 | **512** |
| 40 | BytesPerFileRecordSegment | 以 u32 挤着 512 / 4096 | 4096 / 1024 |
| 48 | ClustersPerFileRecordSegment | 1024 | 1024（= 记录字节数） |
| 56 | MftValidDataLength | 1235484672 | ✓ |
| 64 | MftStartLcn | 786432 | ✓ |

`cluster_size = 29397102 × 60891903` → 字节偏移下溢成 0，
于是报 `MFT 字节偏移无效`。

**改法**：几何信息改从 **NTFS 引导扇区**取（字段偏移由 NTFS 格式规范固定，
可自校验），FSCTL 只保留已验证正确的 `MftValidDataLength@56` 与序列号 `@0`。
新增 `BootGeometry::decode_record_size` 处理引导扇区 `0x40` 的双编码约定
（正数 = 簇数，负数 = 2^(-v) 字节，NTFS 实际用 -10 → 1024）。

### 根因 2：用了目录句柄去读裸扇区（这才是致命的那一个）

即使偏移修对，原代码也**注定读不到数据**：它打开的是 `\?\C:\`
（Win32 目录路径），这种句柄只支持元数据类 `DeviceIoControl`，
按字节偏移 `ReadFile` 直接返回 `ERROR_INVALID_FUNCTION(1)`。

MFT 直读必须用**卷设备路径** `\.\C:`。实测三种路径的可用性：

| 路径 | 非管理员 | 管理员 |
|---|---|---|
| `\?\C:\`（目录） | 可开，但只能做元数据 FSCTL | 同 |
| `\.\C:`（卷设备） | `ERROR_ACCESS_DENIED(5)` | ✓ 可按扇区直读 |
| `\?\C:\$MFT`（文件） | `ERROR_ACCESS_DENIED(5)` | ✓ |

这是 NTFS 的权限约束，不是 bug（WizTree 同样要求管理员）。因此：

- `path_to_volume_device()` / `VolumeHandle::open()` 取代旧的目录句柄打开
- `ERROR_ACCESS_DENIED` 映射为专门的 `NtfsError::NeedAdministrator`，
  错误文案直接给出可操作建议（提权重跑 / `--engine fs`）
- **`detect_best_engine` 增加权限预检**：NTFS **且** 能开卷设备才选 Mft，
  否则回落 Fs。否则默认 `Auto` 会让所有普通用户直接扫描失败
- `is_ntfs_volume` 改用 `GetVolumeInformationW` 判文件系统名——
  读引导扇区需要管理员，不能用来做「是不是 NTFS」的探测

### 顺带修掉的设计缺陷

`close_handle(HANDLE)` 是裸句柄 + 手动关闭，`clippy::not_unsafe_ptr_arg_deref`
报 6 个 error（安全函数解引用裸指针），而且错误分支漏调就泄漏句柄。
改为 `VolumeHandle` newtype + `Drop`，解引用裸指针的 `unsafe`
收敛到 `VolumeHandle::open` 一处，其余读卷函数全部是安全函数。
